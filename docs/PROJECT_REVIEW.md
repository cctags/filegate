# Filegate 与公开文件服务项目的对比评估

评估日期：2026-10-24。本地基线：`66abbd2`，开始时工作区干净。首轮提出后续建议；随后用户选择 MIT，已添加 LICENSE 和 README 授权说明，并补充 CHANGELOG.md。其他新功能、部署配置和发布工作流仍待实施。

## 结论与适用范围

Filegate 已形成清楚的产品边界：Linux/IPv4、Go 标准库、单二进制、管理员本机发码、一次性授权到独立目录、浏览器只读访问。当前最需要补的是公开发布与长期运维配套，其次是诊断和用户体验。没有必要通过增加上传、编辑、WebDAV 或 Web 管理来追求功能数量。

这不是对全部 GitHub 项目的统计，也不是新的渗透测试。比较对象是具体项目的一手文档、发布页面和可读取配置；未测试其运行性能，不能据此给出速度、安全性或维护质量排名。

本地没有配置 Git remote，无法据此确认是否已有独立的远端仓库、手工 Release、保护规则或私密漏洞报告设置。下面“缺少”的文件与自动化均指当前检出的本地仓库，不应推断远端设置。

## 比较对象

| 项目 | 可借鉴的部分 | 与 Filegate 的关系 |
| --- | --- | --- |
| [Dufs](https://github.com/sigoden/dufs) | 有预编译 Releases、配置和权限文档；还提供上传、搜索、WebDAV 等功能 | 借鉴分发和运维，保留 Filegate 的一次性码与本机管理模型 |
| [miniserve](https://github.com/svenstaro/miniserve) | 单二进制、明确示例、截图、文件过滤和排序、TLS | 借鉴安装体验和目录浏览，不必复制全部功能 |
| [copyparty](https://github.com/9001/copyparty) | 多协议、多种部署方案和长期运行说明；有独立 systemd 单元 | 借鉴成熟部署材料；多协议/媒体索引会显著扩大 Filegate 的维护范围 |
| [filebrowser/filebrowser](https://github.com/filebrowser/filebrowser) | 传统 Web 文件管理器，可参考其历史文档与公开安全问题 | 当前页面已标记归档，不作为正在持续提供安全修复的部署推荐 |

上表是功能与交付方式比较，不代表其他项目采用 Filegate 相同的一次性授权机制。Dufs 的 [CI 配置](https://github.com/sigoden/dufs/blob/main/.github/workflows/ci.yaml) 在 PR/分支 push 上执行检查；其 [Release 页面](https://github.com/sigoden/dufs/releases) 提供发行版本。copyparty 提供可直接阅读的 [systemd 服务示例](https://github.com/9001/copyparty/blob/hovudstraum/contrib/systemd/copyparty.service)。这些是可以独立借鉴的工程实践。

## 已经具备、建议继续保留的部分

- 只依赖 Go 标准库、静态构建、明确 Linux/IPv4 支持范围和非 root 服务用户；没有必要为了发布 GitHub 而改语言、引入框架或改成跨平台产品。
- `os.Root` 目录限制、一次性码持久化消费、内存会话、本地管理 socket、永久/临时封禁、同源检查和资源限制；后续便利功能继续遵守这些边界。
- 配置注释、热重载、版本信息、分层帮助、双输出轮转日志和凭据脱敏；这些已经覆盖了相当多实际部署问题。
- 单元/组件、竞态、Unix 协议、实际进程、Chrome 与 fuzz 测试入口；目前重点应是可靠复用这些入口，而非再设一个任意覆盖率目标。
- 不记录明文访问码、Cookie、完整查询和原始任意头；客户端浏览器/时区只作审计说明。不要为追求“更多日志”取消这些约束。

## 第一优先级：公开发布前补齐

### 1. 许可证与安全维护政策

评估时本地没有 `LICENSE` 和 `SECURITY.md`。后续用户已明确选择 MIT，现已添加标准 LICENSE，使用项目通用署名 `Copyright (c) 2026 Filegate contributors`，未填写个人姓名或邮箱。许可证这一项已完成，安全维护政策仍待补充。[GitHub 的许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)区分了公开可见与许可复用。

`SECURITY_REVIEW.md` 是历史审查记录，不能替代面向使用者的维护政策。新 `SECURITY.md` 应简短说明支持哪些版本、如何私下报告问题、应提供哪些脱敏信息，以及当前网络/文件系统边界。联系渠道必须在仓库和维护者身份确定后填写；不要捏造邮箱或承诺无法保证的修复时限。可参考 [Dufs 的安全政策](https://github.com/sigoden/dufs/blob/main/SECURITY.md)。

### 2. 最小 CI 与发布流程

当前本地没有 `.github/workflows`。建议分层，而非每次 push 都执行所有慢检查：

- 常规代码 PR/push：格式检查、`make test`、`make vet`、`make build`；仅文档变更按影响跳过代码检查。
- 影响启动、CLI、重载、持久化：补进程集成；影响登录、Cookie、页面、CSP：补 Chrome；解析或输入校验变化执行相关 fuzz。
- 版本标签、发布或手动完整验证：执行 AGENTS.md 已规定的全套自动化，包括四个 fuzz 各 30 秒。CI 中应确认进程测试以非 root 运行，跳过不能伪装成成功覆盖。

测试 workflow 只给必要读取权限，发布写权限只用于发布任务；第三方 Actions 固定到审核过的提交。定期检查构建工具链安全补丁，并实际使用已有 `make vulncheck` 入口。本轮未发现已安装的 govulncheck，也未执行扫描，不能把先前修复记录当成持续安全检查。[Go 官方漏洞管理工具](https://go.dev/doc/security/vuln/)会结合调用关系分析已知漏洞；纯标准库程序仍需要关注构建工具链。

### 3. 可核对的预编译发行物

先支持实际有需求的 `linux/amd64` 和 `linux/arm64`。它们是 CPU 架构目标，不表示已经支持 Windows/macOS；每个架构分别区分“交叉编译成功”和“实际运行验证”。

建议 Release 提供：

- 以版本/系统/架构命名的压缩包，内含二进制、许可证、简明说明及无凭据的示例。
- `SHA256SUMS` 与验证命令、该版本的变更说明、Go 版本及来源提交。
- 后续有需求再加来源证明或签名。校验和用于核对下载字节，单独放在同一发布页并不等价于独立身份认证。

不必先引入 GoReleaser，现有 Makefile 加小脚本和 Actions 就能完成。打包使用明确文件清单，不能把整个工作目录、tmp 或运行状态压进去。

当前 `VERSION` 来自 git describe，适合开发构建；`BUILD_TIME` 默认取当前时间，因此同一提交的重复构建不保证逐字节一致。若要声称可复现，需固定版本、工具链、构建时间与归档元数据并实际比较产物。没有必要先做出该承诺才能提供可靠下载。

### 4. 版本记录和安装说明

已添加 [CHANGELOG.md](../CHANGELOG.md)，按本地 `v0.1` 标签划分历史版本和 Unreleased，记录用户可理解的变化、兼容性和迁移步骤。正式发布时还需将已验证的未发布条目归入对应新版本，不要求用户从 Git commit 或 SESSION_STATE 推断。

本地 `v0.1` 指向 `122566e`，评估基线 `66abbd2` 在其后 10 个提交。它不代表当前所有功能。正式发布宜采用明确的新版本（如 `v0.2.0`）；已对外发布的标签不再移动，修正使用新版本。本轮不新建或移动任何标签。

仓库地址确定后，README 增加下载、校验、安装和源码构建的独立入口。`go.mod` 当前是 `module filegate`；若准备支持远程 `go install`，应改成实际发布路径并更新内部导入。若只发二进制/克隆后 make build，可暂缓此项。[Go 模块发布说明](https://go.dev/doc/modules/managing-source)解释了路径、源码仓库和版本标签的关系；没有第三方依赖时缺少 go.sum 是正常的，不必补空文件。

## 第二优先级：长期部署和故障处理

### 5. 可使用的 systemd 单元和部署材料

README 已有非登录用户、权限和部分 `[Service]` 配置，基础正确；下一步提供完整的 `deploy/filegate.service` 与步骤：Unit/Install、专用用户、配置路径、日志/状态写权限、`ExecReload`、启动、启用、状态、reload、停止、卸载和升级。

继续使用只读 content、管理员持有的配置，以及服务可写的 state/logs。强化选项必须与实际路径、AF_INET/AF_UNIX、Go 运行及本地 socket 管理一起验证，不能仅复制其他服务的限制。systemd 的 reload 发出 SIGHUP 不等于业务配置已经成功切换，应说明检查重载日志或后续状态。

Docker 不是部署简单性的必要条件：当前单二进制 + 专用用户 + systemd 已适合目标。确有容器使用者后再做精简非 root 镜像、只读内容卷和状态卷说明。

### 6. 无副作用的配置检查

建议新 `check` 操作：在停服/重载前检查配置语法、别名映射、目录重叠、敏感文件位置和可读取条件，不监听、不发码、不覆盖状态、不创建部署数据。错误用明确退出码和可定位信息说明。

不能直接调用当前 `gate.New` 当作无副作用检查，因为它可能创建状态、调整目录权限并保存初始密钥。需要把只读验证与启动初始化拆开复用，并用测试保证现有状态和目录未被改变。只读权限检查不应承诺实际磁盘写入必然成功；需要写入探测时必须另行明确其副作用。

### 7. 升级、备份、恢复与批量失效

README 已提醒恢复旧状态会复活旧码，但缺少完整操作流程。应记录备份哪些文件、何时停服、如何保留权限与密钥、如何替换/回退二进制、恢复后如何处理旧访问码，以及重启后会话全部失效。

有实际需求时增加本地“撤销全部未用码/撤销全部会话”的操作，避免事故处置依赖手工编辑 state.json。它与现有按 ID revoke、按别名 logout 的关系应明确，不能顺手改变封禁名单。

未来第一次修改状态格式前，加入格式版本及迁移/拒绝策略，测试“无法识别的新版本失败但不覆写文件”。当前 State 只有 Secret/Codes/Bans，没有 schema 版本；这属于演进准备，不代表当前必须换数据库。单进程原子文件写入仍适合目前规模，跨黑名单/状态文件的部分失败继续按现有文档处理。

### 8. 先扩展本地诊断，按需增加监控

当前 `status` 已有代码/封禁/会话概况。可增加服务版本、启动时间、最近成功重载时间及不含凭据的计数，帮助确定“运行中的程序是哪一个版本”。磁盘上的 `--version` 不能独自证明旧进程已升级。

优先使用现有私有 Unix 管理接口。不必为了其他项目有 healthcheck 就立即增加公开 HTTP 状态接口；确有容器探针需求时再定义不泄密的 liveness/readiness。JSON 日志或指标同样按实际日志平台需求增加，不开放任意头/查询格式模板。

## 第三优先级：使用体验与内部维护

- 文件列表可增加易读文件大小、修改时间、当前目录内的名字过滤和排序。当前已有上级目录链接、中文名和显式下载入口，避免重复开发。过滤必须限制在当前授权目录，继续遵守条目上限；递归索引、缩略图、全文搜索不列为本阶段目标。miniserve 的[名字过滤/排序功能](https://github.com/svenstaro/miniserve)可作界面参考。
- 补少量真实 PDF、音频和移动浏览器的发布验收，Firefox 另行执行或实现合适的 runner；当前 Chrome CDP 不意味着 Firefox 已测。保留正常情况下无脚本也能登录的约定。
- 将 `http.go` 的长单行模板移为格式化的嵌入 HTML/CSS，仍编入单个二进制。移动时检查模板转义、固定时区脚本及 CSP 哈希，不顺便开放用户 HTML 执行。CLI 帮助的文本与格式化逻辑也可分文件，暂不继续扩大颜色解析器。
- 默认配置、help 的默认值表和 README 示例存在多份文字。先加一致性测试或复用少量默认常量，减少改一处漏另一处；不要为此建设复杂配置生成平台。
- 命令名/参数数量在解析和帮助中各有定义，后续增加命令时可统一命令元数据，避免新操作有实现却没有帮助。
- 增加小规模性能基线：目录几百/几千文件、并发下载、发码写状态、封禁文件读取、慢客户端下管理响应。测量 CPU/内存/文件描述符后再优化；目前不能根据“Go/标准库/静态链接”推导吞吐或资源占用优于其他项目。

## 建议精简或归档的内容

1. **README 的历史说明**：保持定位、截图、安装、快速开始、限制与文档链接；详细操作/开发/审查放 docs。先分层，不删除必要的安全边界与恢复说明。
2. **SESSION_STATE 的旧当前状态**：顶部仍有较早基线、旧 Go/版本快照和过时恢复提示。保留简短的真实恢复入口，将长历史移入有日期的归档；历史保留，不再与当前状态并列冒充最新。
3. **AGENTS 与多份测试规则**：保留必须遵守的约束和清晰入口，详细测试矩阵集中维护并链接，减少重复拷贝导致的冲突。AGENTS 是开发指导，另加简短 CONTRIBUTING 面向普通贡献者即可。
4. **本地 tmp**：缓存、报告和实验脚本已忽略；需要空间时可提供分类清理入口，但必须保护用户 demo、现有内容/状态和可能运行的服务。没有依据删除它们，也不把 tmp 证据当成仓库可重建功能。
5. **重复或仅镜像实现的测试**：逐项审查断言价值后再合并；不按代码行数、测试数量或覆盖率盲目删减现有安全回归。

本轮没有发现“必须立刻删除才能正常使用”的已提交文件。上述精简是文档和维护方式建议，不是清空用户工作目录或重写 Git 历史的授权。

## 暂不增加的功能

- Web 管理员后台、长期账号系统、多租户平台：会改变本机管理和一次性码的基本产品模型。
- 上传/编辑/删除、ZIP 自动解压、在线命令执行：需要新的权限、配额、磁盘与文件安全模型；存在实际业务需求后单独设计。尤其不引入命令执行/钩子来追求“通用”。
- HTML/Markdown 可执行预览、插件前端：当前源码预览继续保留；未来若确需渲染，应先设计内容与会话来源隔离。
- 自动信任代理转发头、恢复 IPv6、跨平台适配：这些是明确的部署/范围决策，不能为与同类项目列表一致而改动。
- 数据库、第三方 Go 框架、GoReleaser、自动更新器、Prometheus、Kubernetes/Helm、包管理器多渠道、成排徽章：都不是当前公开发布的前置条件。校验、安全和版本可信比装饰完整更优先。
